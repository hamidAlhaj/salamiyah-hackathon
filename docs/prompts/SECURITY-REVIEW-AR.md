# مراجعة أمنية وإصلاحات لمنصة تبرعات مجلس سلمية

اعمل داخل النسخة الحالية من مستودع Majlis Fund بصفتك مهندس أمن تطبيقات ومطوراً مسؤولاً عن الإصلاح والاختبار. راجع موقع Next.js وتطبيق Expo/React Native وخادم NestJS وقاعدة PostgreSQL عبر Prisma. نفّذ الإصلاحات المحلية المحددة التي تدعمها أدلة من الكود، ثم اختبرها وأعطِ الفريق ملخصاً بالعربية. إذا لم تجد مشكلة مثبتة تستدعي تعديلاً، اشرح ما تحققت منه وحدود التغطية.

## 1. ثبّت نقطة البداية

- اقرأ تعليمات المستودع المنطبقة، خصوصاً `CLAUDE.md` و`README.md` و`DEMO.md`. تحقّق من السلوك الفعلي والعقود والاختبارات. تعامل مع مقترحات العمل السابقة كمراجع لفهم المتطلبات. نطاق التنفيذ هنا هو المراجعة الأمنية والإصلاحات المرتبطة بها.
- سجّل الفرع ونسخة HEAD وحالة Git، وحدد ملفات الفريق المعدّلة أو غير المتتبعة. حافظ على عملهم. إذا تعارض إصلاح مع تعديل جارٍ يصعب دمجه بأمان، اترك الجزء المتعارض واشرح القرار المطلوب. أبقِ التغييرات محلية للمراجعة دون commit أو push أو نشر.
- اقرأ ملفات الحزم والقفل في `api/` و`web/` و`mobile/` و`e2e/`. شغّل خط أساس للفحوص ذات الصلة قبل التعديل. تحقق من وجهة قاعدة البيانات وعناوين الخدمات قبل أي اختبار يكتب بيانات، واستخدم قاعدة اختبار مستقلة وبيانات وهمية. احجب الأسرار عند عرض الإعدادات. تجنّب أوامر reset وإعادة تهيئة بيانات الفريق.

## 2. تتبّع المسارات الحساسة من الواجهة إلى قاعدة البيانات

استرشد ببنود OWASP ASVS وAPI Security وMASVS التي تنطبق على الكود الموجود. افحص الاستدعاء من Server Actions وصفحات الويب و`web/src/lib/api/` أو من `mobile/src/lib/api.ts`، ثم تتبع الـcontroller والـguard والـDTO والخدمة واستعلام Prisma والاستجابة. تحقّق أيضاً من المسارات العامة ومسارات تنزيل الملفات التي يمكن الوصول إليها مباشرة.

| المجال | ما يجب التحقق منه |
| --- | --- |
| الحساب والجلسة | راجع التسجيل والدخول والخروج وانتهاء JWT وتعطيل الحساب وتغيير الدور. تحقّق من حماية ملف تعريف الارتباط HttpOnly ومن فرض صلاحيات Server Actions ومن ضوابط CSRF المناسبة. راجع ما يُرسل إلى Redux أو المتصفح وما يُحفظ عبر طبقة تخزين Expo وما يُزال عند الخروج. التزم بنموذج المصادقة المعتمد في المشروع. |
| الصلاحيات والخصوصية | ابنِ مصفوفة المورد والعملية والأدوار الستة من الكود، مع شرط الملكية أو الإسناد حيث يلزم. اختبر بحسابَي متبرع مختلفين وبأدوار الموظفين المعنية. غطِّ الملفات الطبية وإثباتات التحويل والصرف والاستيراد والإشعارات. ميّز بين التحقق العام المقصود من الإيصال الرسمي عبر `GET /official-receipts/:no` وبين تنزيل ملف الإثبات المحمي عبر `GET /receipts/:id/file`. حافظ على التحقق العام وافحص حقوله، واختبر قيود الملكية والدور على الملف الخاص. افحص هوية المستفيدين في استجابة لوحة الشفافية نفسها، بما فيها الروابط والحقول المتداخلة. |
| التبرعات والصرف | تتبّع التعهّد والاستلام والتحقق والإيصال والإشعار والقيد المالي. اختبر التبرع لصندوق المجلس، والحملة القريبة من هدفها، وموافقة المتبرع على توجيه الفائض، واختيار المبلغ المتبقي أو الانتقال إلى حملات أخرى أو الإلغاء وفق السلوك المعتمد. افحص إعادة المحاولة بعد انقطاع الشبكة وتزامن تأكيدين. تحقّق من الأرصدة والإيصالات بعد العملية ومن عدم احتساب المال مرتين أو تسجيل حركة عند الإلغاء. راجع حدود دور `COLLECTOR` في التحصيل النقدي وحافظ على تسميته العربية المعتمدة «مكي» حيث تُستخدم. |
| المدخلات والملفات | راجع التحقق على الخادم من الحقول المسموحة والملكية والحالة والمبالغ، والاستعلامات الخام إن وجدت، والسياقات التي تعرض HTML أو تفتح روابط. افحص صلاحية تنزيل الملف ونوعه الفعلي وحجمه ومساره، وحدَّي 5 MB للمستندات الطبية والإيصالات و10 MB للاستيراد. اختبر حد الحجم نفسه وما فوقه عند الطبقات التي تمر بها العملية. تتبّع انتقال الاستيراد بين المعاينة والتحقق والاعتماد. |
| الويب والموبايل والإعدادات | راجع حدود server-only، وعزل التخزين المؤقت لبيانات المستخدمين، وCORS، وضبط المعدّل للعمليات الحساسة، وتسريب البيانات في الأخطاء والسجلات. افحص روابط Expo العميقة وفتح الإيصالات والصلاحيات وإعدادات الإصدار. حافظ على إمكانية تشغيل العرض المحلي عبر Expo وشبكة Wi-Fi، مع بقاء إعدادات اتصال الإنتاج آمنة. افحص الأسرار في الملفات والحزم العامة دون نسخ قيمها. |
| الاعتماديات | افحص إصدارات ملفات القفل، وميّز بين اعتماد وقت التشغيل وأداة التطوير. اربط التنبيه بالاستخدام الفعلي وحدد أصغر تحديث متوافق، مع مراعاة توافق Expo وReact Native. تجنّب التحديثات الجماعية و`npm audit fix --force`. |

## 3. قواعد قرار الإصلاح

- صنّف النتيجة إلى خلل مثبت، أو ملاحظة تحتاج تحققاً، أو تحسين دفاعي. استند إلى ملف وسطر ومسار بيانات أو اختبار محلي قابل للتكرار. سجّل الأثر والأولوية. يكفي الدليل من الكود واختبارات سلوك التطبيق ببيانات وهمية. ابدأ بالأثر الأعلى.
- نفّذ أصغر إصلاح يعالج السبب في الطبقة المسؤولة، وابحث عن المواضع الأخرى التي تستخدم المنطق نفسه. حافظ على تقسيم الحزم والوحدات، ومسارات العرض، والعربية والإنجليزية وRTL، وأسلوب معالجة الأخطاء. أبقِ التحسينات الشكلية وإعادة الهيكلة العامة خارج التغيير.
- عند تغيير استجابة كانت تكشف معلومات خاصة، حدّد المستهلكين في الموقع والموبايل واختبر البديل المشروع. عند تعديل نوع مشترك، افحص النسخ المناظرة في `api/src/common/shared/` و`web/src/shared/` و`mobile/src/shared/` وحقّق قواعد المزامنة المعتمدة للملفات المشتركة.
- لا تُخفِ المشكلة بتعطيل ميزة أو حذف مسار أو إضعاف تحقق أو تخطّي اختبار. إذا احتاج الإصلاح قراراً في قواعد التبرع أو الصلاحيات، أو تغيير عقد يكسر عميلاً قائماً، أو ترحيل بيانات قائم، اشرح الخيارات والأثر وطريقة التراجع واطلب موافقة الفريق قبل تنفيذ الجزء المعني. أكمل الإصلاحات المستقلة. تعامل مع تدوير الأسرار وإعدادات النشر كإجراءات منفصلة يملكها الفريق.

## 4. اختبر الإصلاح والوظيفة معاً

لكل إصلاح أضف أو حدّث اختبار انحدار محدداً حيث يتاح ذلك. مثال: المتبرع يستطيع تنزيل إثباته، ويُرفض تنزيل الإثبات نفسه من حساب آخر، وتستمر صفحة التحقق العام في إظهار الحقول المسموحة. اختبر من نقطة الدخول الطبيعية للعملية. أظهر نتيجة الاختبار قبل الإصلاح وبعده متى أمكن.

نفّذ الأوامر من مجلد الحزمة المعنية وتحقق من تعريفاتها في النسخة الحالية. سجّل أي عائق كما وقع.

| المجلد | الفحوص المتاحة في المشروع |
| --- | --- |
| `api/` | `npm test -- --runInBand` و`npm run build`. لفحص lint دون تعديل الملفات استخدم `npm exec -- eslint "{src,test,prisma}/**/*.ts"`، لأن سكربت lint الحالي يضيف `--fix`. |
| `web/` | `npm test` و`npm run lint` و`npm run build`. اختبر أيضاً سلوك Server Action أو الشاشة المتأثرة بالجلسة والدور المناسبين. |
| `mobile/` | `npm run typecheck` و`npm run lint`. جرّب التدفق المتأثر عبر Expo على جهاز أو محاكي متاح. اذكر المنصة وأي خطوة تحتاج تجربة فعلية على هاتف. |
| `e2e/` | راجع إعداد Playwright وعناوين الخوادم أولاً. شغّل `npm run test:smoke` و`npm run test:scenario` بحسب أثر التغيير، على API وويب يعملان بقاعدة الاختبار. |

عند تغيير عقد مشترك، اختبر المسار من العميلين حيث يُستخدم. قارن النتائج بخط الأساس وافحص الفرق النهائي للتأكد من اقتصاره على الإصلاح واختباراته. إذا أدخل تعديلك فشلاً، عالجه وأعد الفحص أو اسحب تعديلك المحدد مع حفظ عمل الفريق. أوقف فقط الخدمات المؤقتة التي شغّلتها للمراجعة.

## 5. سلّم الفريق ملخصاً بالعربية

1. **الخلاصة.** ما الذي راجعته؟ ما أهم إصلاح؟ وهل يوجد ما يتطلب قراراً قبل الدمج؟
2. **جدول النتائج.** لكل نتيجة اذكر الأولوية والثقة، الملف والسطر، الدليل والأثر، ما أصلحته أو سبب بقائه مفتوحاً، والوظيفة التي اختبرتها بعد الإصلاح. افصل التحسينات الدفاعية عن الثغرات المثبتة.
3. **التحقق الفعلي.** اعرض الأمر أو التجربة، الحزمة أو الجهاز، النتيجة قبل وبعد، وأي فشل سابق أو فحص تعذّر تشغيله وسببه. اذكر صراحةً مستوى التحقق على الموبايل: فحص أنواع، بناء حزمة، متصفح، محاكي، أو هاتف.
4. **التسليم.** اذكر الملفات المعدلة وسبب كل مجموعة تغييرات، ثم الإجراءات اليدوية المتبقية والمسؤول عنها وكيف يتحقق الفريق من نجاحها. اختم بحالة واضحة: جاهز للمراجعة، أو يحتاج قراراً، أو يحتاج تحققاً إضافياً مع تحديده.
